### Slide 3：系统总体架构与混合组网（约 45 秒）

**【PPT 画面】** 三种架构方案对比 + 图 2-1 系统分层与网络混合架构图。

**【讲稿】**
> 在架构选型上，我们对比了纯 TCP 的 C/S 模式和纯 UDP 广播的 P2P 模式：纯 TCP 需要每台电脑手动查 IP，纯 UDP 广播则不可靠且很难做私聊与文件传输。

### Slide 4：自定义应用层协议设计（约 50 秒）

**【PPT 画面】** 图 3-1 4 字节大端长度头帧格式与粘包拆包图 + 20 种消息类型分组。

**【讲稿】**
> 这一页是本项目最核心的计网知识点——如何解决 TCP 面向字节流导致的**粘包与拆包**问题。  
> 我们设计了「**4 字节大端无符号长度头 + UTF-8 JSON 载荷**」的二进制帧格式：发送端用 `struct.pack("!I", len)` 写入网络字节序的长度值 `N`，并限定单包上限为 1 MB 防止恶意大包耗尽内存；接收端先通过循环定长读取函数 `recv_exact(sock, 4)` 读出长度 `N`，再精确读出 `N` 字节做 JSON 反序列化。  
> 在这套帧结构上，我们一共规范了 **20 种应用层消息类型**，涵盖登录认证、房间群聊与私聊、ACK 送达与已读回执、历史同步、房间管理、分块文件传输以及心跳保活。

### Slide 5：全流程协议交互时序（约 40 秒）

**【PPT 画面】** 图 3-2 客户端 A — 服务端 — 客户端 B 全流程时序图。

**【讲稿】**
> 这张时序图串起了系统完整的一次生命周期：  
> 启动阶段，客户端向 `255.255.255.255:9999` 广播 `DISCOVER_LAN_CHAT_V1` 探测包，服务端单播回复 TCP 端口；随后建立 TCP 三次握手并发送 `LOGIN` 认证，成功后同步在线用户、房间列表与历史记录。  
> 聊天阶段，客户端发出带唯一 `msg_id` 的消息后，服务端落库并立即回 `MSG_ACK`，转发给接收方；接收方查看后上报 `MSG_READ`，原发送方实时变成双勾已读。大文件则按 `FILE_META → N 个 FILE_CHUNK → FILE_END` 流式传输，全程配合周期心跳保活。

### Slide 6：服务端并发模型与核心保障（约 40 秒）

**【PPT 画面】** 多线程并发结构、两级锁粒度说明、UDP 发现兜底、30 秒心跳守护。

**【讲稿】**
> 服务端在并发控制上重点解决了两个工程痛点：  
> 第一是**多线程并发写同一 Socket 导致帧交错**的问题。我们设计了两级细粒度锁：全局 `_clients_lock` 只在读写在线字典和拷贝目标列表时短暂加锁，绝不在锁内做网络发送；而每个客户端会话 `ClientSession` 拥有独立的 `send_lock`，保证「4 字节帧头 + JSON 体」作为一个原子帧完整写出。  
> 第二是**半开连接（僵尸连接）清理**。客户端每 10 秒发一次心跳，服务端用单调时钟 `time.monotonic()` 刷新活跃时间，后台守护线程定期扫描超过 30 秒无响应的连接并主动关闭回收，同时广播下线通知。

### Slide 7：高级特性 ① —— SQLite 持久化与多房间路由（约 35 秒）

**【PPT 画面】** 图 5-1 SQLite 三表 ER 关系图 + 多房间隔离策略。

**【讲稿】**
> 为了让系统更贴近真实即时通信软件，我们用 Python 内置 `sqlite3` 设计了 `rooms`、`messages`、`read_receipts` 三张持久化表，并在 `(conv_type, conv_id, id)` 上建了复合索引。私聊会话通过字典序拼接 `pm:Alice::Bob` 保证双向唯一。服务端重启后，所有房间、聊天记录和已读状态完整保留。  
> 在群组方面，服务端为每个连接维护所属房间集合，通过 `_broadcast_room` 按房间成员路由转发，未加入自定义房间的用户不会收到该房间内的任何消息与文件，实现逻辑多播隔离。

### Slide 8：高级特性 ② —— ACK 回执、已读状态与自动重连（约 35 秒）

**【PPT 画面】** 三态消息状态流转图 + 指数退避重连机制（`1s → 2s → 4s → 8s → 10s`）。

**【讲稿】**
> 在应用层可靠性上，每条消息都对应「**发送中 → ✓ 已送达 → ✓✓ 已读**」三态流转，让用户明确知道消息不仅发出去了，而且已被服务端持久化落库并被对方阅读。  
> 面对局域网 Wi-Fi 抖动或服务端重启，客户端内置了**指数退避自动重连机制**：断线后等待时间按 `1s、2s、4s、8s` 递增（上限 `10s`），避免重连风暴；连上后自动重新登录、自动重新加入断线前的所有自定义房间，并触发历史消息补拉，做到无感恢复。

### Slide 9：高级特性 ③ —— 48 KB TCP 分块文件与图片传输（约 40 秒）

**【PPT 画面】** 图 5-2 48 KB TCP 分块传输与 SHA-256 校验流水线。

**【讲稿】**
> 如果直接把几兆的图片打包成一个巨型 JSON 发出去，不仅会触发 1 MB 单包拦截，还会引发**队头阻塞**卡死普通聊天。  
> 因此我们将文件按 **48 KB/块** 切分，Base64 编码后每帧约 64 KB，通过后台线程依次发送 `FILE_META`、多个带序号 `seq` 的 `FILE_CHUNK` 和 `FILE_END`；每块独立申请发送锁，文字和心跳可以在分块间隙穿插通过。  
> 接收端按序号实时重组并推送进度条，收齐后计算 **SHA-256 摘要** 与发送端比对，校验通过后图片直接气泡内联预览、点击放大，文档支持一键原名下载。

## 三、老师高频提问 Q&A 锦囊（提前背熟稳拿高分）

### Q1：TCP 本身已经是可靠传输协议了，为什么应用层还要设计 `MSG_ACK` 和 `SHA-256` 校验？
> **参考回答**：TCP 的可靠传输只保证“字节流可靠到达对端操作系统内核的接收缓冲区”，并不保证**应用进程已经成功解析并持久化到数据库**（例如内核收到后服务端进程突然崩溃）。应用层 `MSG_ACK` 是在写入 SQLite 后才发回的，代表业务级可靠落库；同理，TCP 校验和只有 16 位且仅覆盖传输层分片，端到端 `SHA-256` 校验能验证应用层切片、Base64 编解码、按序重组全过程零差错。

### Q2：你们是怎么解决 TCP 粘包和拆包的？为什么不用 `\n` 换行符分隔？
> **参考回答**：我们采用「4 字节大端无符号长度头 (`!I`) + UTF-8 JSON 体」的定长前缀协议，接收端用 `recv_exact()` 循环读取精确字节数。相比 `\n` 分隔符法，长度前缀法无需扫描正文转义特殊字符、天然支持消息内容中包含换行符与任意二进制 Base64 块，且读取长度头后即可第一时间拦截超过 1 MB 的非法大包，解析效率更高、更安全。

### Q3：UDP 广播自动发现的原理是什么？如果两台电脑不在同一个子网还能发现吗？
> **参考回答**：客户端开启 `SO_BROADCAST` 套接字选项，向受限广播地址 `255.255.255.255:9999` 发送魔数探测包，同局域网内监听 UDP `9999` 的服务端收到后向源地址单播回复自己的 TCP 端口。由于路由器默认不会转发二层/三层受限广播包，因此 UDP 广播仅在**同一局域网广播域（同一子网）**内生效；跨网段场景下客户端支持手动输入服务端 IP 直连。

### Q4：多线程服务端同时给同一个客户端转发群聊消息和文件分块，会不会串包？怎么避免死锁？
> **参考回答**：不会串包。我们为每个连接对象 `ClientSession` 配备了独立的发送互斥锁 `send_lock`，保证一条完整帧（长度头 + JSON 体）原子写出。在避免死锁方面，全局在线表锁 `_clients_lock` 只在内存中拷贝目标会话列表时短暂持有并立即释放，绝不在持有 `_clients_lock` 时去获取任何 `send_lock` 或执行阻塞 I/O，消除了嵌套锁导致的死锁条件。

### Q5：发文件为什么要按 `48 KB` 分块，而不是一次性把整个文件塞进一个 JSON 包？
> **参考回答**：第一，单包太大容易突破应用层 `1 MB` 防护上限且瞬时内存峰值高；第二，如果在一条 TCP 连接上一次性写入 10 MB 巨包，会造成严重的**队头阻塞**，导致普通文字聊天和 10 秒心跳包超时断开；第三，按 `48 KB` 切片（Base64 后约 `64 KB`）每块独立加锁发送，可以让聊天和心跳帧穿插通过，还能实时精确驱动前端传输进度条。

### Q6：浏览器界面为什么没有用 WebSocket，而是用 `HTTP + SSE` 桥接？
> **参考回答**：本项目坚持**零第三方库依赖**且要求局域网链路跑的是**自定义裸 TCP 协议**（方便计网抓包）。浏览器无法直接操作原生 TCP Socket，而 Python 标准库自带 `http.server` 但没有自带 WebSocket 库；用标准库实现 `POST` 上行 + `SSE (text/event-stream)` 下行推送，仅需几十行纯标准库代码即可获得低延迟实时体验，同时局域网抓包看到的依然是纯正的自定义 TCP 协议帧。

### Q7：如果并发用户从局域网几十人扩大到几千人，当前多线程模型有什么瓶颈？如何改进？
> **参考回答**：当前每连接一线程模型在几十到几百并发下代码清晰、性能足够；但如果扩展到数千并发，操作系统线程栈内存开销（每线程约几 MB）和频繁上下文切换会成为瓶颈。改进方案是将服务端 I/O 模型重构为基于 `selectors`（Linux 底层 `epoll`）或 Python `asyncio` 的事件驱动 I/O 多路复用架构，用单线程事件循环配合非阻塞 Socket 状态机支撑高并发。

### Q8：断线自动重连的指数退避是什么意思？为什么不每 0.5 秒一直重试？
> **参考回答**：如果服务端短暂重启，所有客户端每 0.5 秒死循环重连会瞬间产生「惊群效应 / 重连风暴」把刚启动的服务端再次打垮。指数退避将重连间隔按 `1s → 2s → 4s → 8s`（上限 `10s`）指数拉长，既能在短暂抖动时 1 秒快速恢复，又能在长时间断网时大幅降低客户端 CPU 与局域网无效 SYN 报文开销。
